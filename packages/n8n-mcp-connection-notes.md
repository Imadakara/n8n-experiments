# n8n ↔ Claude MCP connection — статус и как это заработало

Дата: 2026-07-07
Статус: **MCP-соединение работает.** Осталось починить отдельный баг n8n с тумблером "Available in MCP" (см. раздел "Текущий блокер" внизу).

## Цель

Подключить локально установленный n8n (Windows, запускается через `npx`/`npm`) к Claude через MCP, чтобы Claude мог напрямую искать/запускать (а в перспективе — создавать) воркфлоу.

## Окружение

- ОС: Windows (устройство "asus-vivobook")
- n8n: запускается локально через `npx`/`npm` (`n8n start`), порт 5678
- Node.js: v22.22.3 / v20.20.2 (в разных процессах), npx 10.9.8
- Приложение: Claude (Cowork desktop app), НЕ классический "Claude Desktop"
- Реальный файл настроек приложения (важно — не `%APPDATA%\Claude\...`, а):
  `C:\Users\PC\AppData\Local\Packages\Claude_pzs8sxrjxfjjc\LocalCache\Roaming\Claude\claude_desktop_config.json`
  (приложение поставлено как packaged/MSIX, поэтому обычный `%APPDATA%` путь не тот)

## ✅ РАБОЧАЯ КОНФИГУРАЦИЯ (финальная)

В файле конфига выше, ключ `mcpServers`:

```json
{
  "mcpServers": {
    "n8n-mcp": {
      "command": "C:\\Users\\PC\\AppData\\Roaming\\npm\\mcp-remote.cmd",
      "args": [
        "http://localhost:5678/mcp-server/http",
        "--header",
        "Authorization: Bearer <ACCESS_TOKEN>"
      ]
    }
  }
}
```

Плюс обязательные предварительные шаги:

1. В n8n: Settings → Instance-level MCP → включить, Connection details → вкладка **Access Token** → сгенерировать токен (вставляется в конфиг выше вместо `<ACCESS_TOKEN>`).
2. Пакет `mcp-remote` установлен **глобально** (не через `npx -y` при каждом запуске!):
   ```powershell
   npm install -g mcp-remote
   ```
   Команда в конфиге указывает на прямой путь к глобально установленному бинарнику (`C:\Users\PC\AppData\Roaming\npm\mcp-remote.cmd`), а не просто `"npx"` или `"mcp-remote"" — так обходятся сразу два бага (см. ниже).
3. Полный перезапуск Claude Desktop через трей (Quit → открыть заново) после любого изменения конфига.
4. **Важно:** соединение подхватывается только в **новых** беседах/чатах — уже открытый чат, где инструменты не были доступны на момент старта, их не подхватит даже после переподключения. Проверять нужно в свежем чате.

Туннель ngrok для этого способа **не нужен** — процесс `mcp-remote` запускается локально на компьютере пользователя тем же приложением Claude Desktop (через `mcpServers`), поэтому обращается к n8n напрямую по `localhost`, а не из облака.

## Как дошли до рабочего варианта — три найденных и обойдённых бага

### Баг 1: официальный облачный коннектор "n8n" (Directory → n8n) нестабилен для self-hosted

- Требует URL вида `https://<домен>/mcp-server/http` (не просто домен) — обычная ошибка на старте: "Server URL doesn't match expected format".
- Даже с правильным URL OAuth-хендшейк ломается: `Couldn't register with n8n's sign-in service` (`ofid_...`). По отчётам сообщества n8n, это либо баг Claude (не прикладывает Bearer-токен после OAuth), либо проблема с заголовками прокси (`X-Forwarded-For`) — в любом случае, для self-hosted + туннель ngrok сейчас нестабильно. **Отказались от этого пути.**

### Баг 2: приложение Claude неправильно подставляет путь с пробелом на Windows

- При `"command": "npx"` приложение само резолвит полный путь (`C:\Program Files\nodejs\npx.cmd`) и передаёт в `cmd.exe` **без кавычек** → команда обрывается на пробеле: `'C:\Program' is not recognized...`.
- **Обход:** указывать в `command` уже готовый абсолютный путь без пробелов (`C:\Users\PC\AppData\Roaming\npm\mcp-remote.cmd` — под `AppData\Roaming\npm` пробелов нет), либо оборачивать всё через `cmd /c "..."` (рабочий, но более хрупкий вариант — см. Баг 3).

### Баг 3: битый кэш `npx` + баг с кавычками при обёртке в `cmd /c "строка"`

- Каждый `npx -y <пакет>` пере-качивает/распаковывает пакет во временный кэш `%LOCALAPPDATA%\npm-cache\_npx\...`. На этой машине распаковка периодически падала (`EPERM: operation not permitted, unlink`, `TAR_ENTRY_ERROR`), из-за чего пакет оставался частично распакованным → `Cannot find module ... is-promise.js`, `Cannot find module './db.json'` при следующем запуске.
- Отдельно: если оборачивать всю команду в одну строку `cmd /c "npx ... --header \"Authorization: Bearer TOKEN\""`, вложенные кавычки не переживают повторный разбор `cmd.exe` — заголовок обрезается (`Warning: ignoring invalid header argument: "Authorization:`), из-за чего `mcp-remote` не видит токен и сам пытается запустить OAuth (которая у n8n падает с `Internal Server Error` при обмене кода на токен — отдельный баг n8n, который просто не встретился в финальной версии, так как OAuth-путь больше не используется).
- **Обход (финальный):** установить `mcp-remote` глобально (`npm install -g mcp-remote`) — это устраняет пересборку/распаковку кэша `_npx` при каждом запуске — и указывать прямой путь к бинарнику + аргументы отдельным JSON-массивом (не одной строкой через `cmd /c`), чтобы избежать повторного разбора кавычек.

## Как удостоверились, что соединение реально работает (не просто "выглядит правдоподобно")

1. Независимая проверка через **MCP Inspector** (`npx @modelcontextprotocol/inspector`, Streamable HTTP, `http://localhost:5678/mcp-server/http` + Bearer-токен) — подключился мгновенно, `tools/list` вернул реальные инструменты (`search_workflows`, `execute_workflow`, `get_workflow_details` и др.). Это доказало, что сам MCP-сервер n8n полностью исправен, независимо от Claude.
2. После финальной конфигурации — в **новом** чате Claude реально загрузил инструменты `n8n-mcp` и вызвал `search_workflows`. Набор названий инструментов, которые Claude перечислил в том чате, **точно совпал** с тем, что показал MCP Inspector — то есть это не выдумка модели, а реальный ответ сервера.

## Текущий блокер (не наша конфигурация, баг в самом n8n)

`search_workflows` возвращает пустой список, хотя тестовый воркфлоу ("Test") реально существует и виден в UI n8n. Причина — подтверждённый открытый баг n8n:

- В UI n8n есть тумблер/пункт контекстного меню **"Enable MCP"** / "Available in MCP" для воркфлоу.
- Тумблер можно включить, но при переходе в сам воркфлоу, в его настройки, или **при обновлении страницы (F5)** — состояние сбрасывается обратно на выключено.
- Соответствует открытому GitHub issue **n8n-io/n8n #25987** — "Available in MCP toggle not persisting", статус на момент написания — не решён (needs-info).
- Пока тумблер не сохраняется, ни один воркфлоу не может попасть в список, видимый через `search_workflows`, — это ограничение на стороне n8n, а не проблема MCP-соединения или конфигурации Claude.
